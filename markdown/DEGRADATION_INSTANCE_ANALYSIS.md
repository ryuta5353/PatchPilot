**目的**: RepoGraph グラフ情報を取得して精度が下がった実際のインスタンスの共通パターンを特定

**データ出所**: Phase 2-6 調査結果（23インスタンス、ベースラインと比較）

## 3. グラフ情報が悪化させるメカニズム

### 3-1. グラフが多いと何が起こるか

```
84個の関数定義がグラフコンテキストに含まれる場合：

1. 各関数 = 100-300トークン
2. 84個 × 200トークン = 16,800トークン（グラフだけで）
3. LLM が 84個すべてを読む
4. 「どの行を修正するのか」を判断が困難
5. ランダムな推測 → 精度低下
```

### 3-2. ラインレベルで悪化する理由

**ファイルレベル**（グラフで改善）:
```
問題：「どのファイルを修正？」
グラフ情報：「このファイルは他の 10個ファイルを呼び出し、
             5個ファイルから呼ばれています」
効果：「このファイルは重要な依存関係がある」
     → ファイル選択が改善 ✓
```

**ラインレベル**（グラフで悪化）:
```
問題：「どの行を修正？」
グラフ情報：「このファイルに 84個の関数があります。
             それぞれの定義、パラメータ、呼び出し関係があります」
効果：「どれを修正すればいい...？」
     → LMが混乱、精度低下 ✗
```

### 3-3. トークン予算オーバーランの問題

```
予算:       30,740 tokens
実際の使用:  33,313 tokens (8.4% オーバー)

ワーストケース:
- sphinx-doc__sphinx-8595: 51,170 tokens (1.7倍！)
- astropy__astropy-12907:  69,938 tokens (2.3倍！！)

結果：
- グラフコンテキストが大きすぎる
- ファイル内容が削減される
- 元のコンテキストが失われる
- さらに精度低下
```

## 6. グラフ利用が悪化する理由の根本

### 根本原因 1: スコアリングが「構造的」で「意味的」ではない

```
現在のスコアリング（Composite Score）:
  score = file_locality (1000/100/1)
        + direct_neighbor_count
        + in_degree_count

このスコアは「どのファイルが構造的に関連しているか」を示す

しかし問題解決には：
  「この行を修正する必要がある」
  ↑ 意味的な関連性が必要

構造的に関連 ≠ 意味的に関連
```

### 根本原因 2: 関数数が多すぎると LLM が混乱

```
最良の例（改善）：8個の関数
  → LLM: 「8個から選べばいいね」
  → 比較的容易

ワーストの例（悪化）：84個の関数
  → LLM: 「84個...？」
  → パニック → ランダムな推測 → 外す

理想的な個数：6-10個
許容範囲：15-20個
問題範囲：50個以上
```

### 根本原因 3: グラフコンテキストが「ノイズ」になる

```
ファイルレベルでは：
  グラフが「このファイルは重要」という証拠になる
  → ファイル選択改善 ✓

ラインレベルでは：
  グラフが「これらすべての行が関連」という信号になる
  → 修正行を特定できない
  → ノイズ化 ✗
```

## 8. RepoGraph 統合が失敗した理由の要約

| 理由 | 影響度 | 詳細 |
|------|--------|------|
| **グラフが大きすぎる** | 高 | トークン予算超過（1.7-2.3倍）、予測不可 |
| **関数数が多い** | 高 | 84個の関数から行を選ぶのは困難 |
| **スコアリングが構造的** | 高 | 意味的な関連性ではなく構造的なのみ |
| **トークン管理の失敗** | 中 | Greedy allocation が機能していない |
| **ファイル削減による損失** | 中 | グラフのためにファイル内容が削減される |
| **サイレント失敗** | 中 | 4インスタンスが処理完了しない |

## 9. 推奨される改善戦略

### 短期（すぐに実装可能）

1. **グラフサイズ制限**
   - 関数数: 最大 15個
   - セクション数: 最大 10個
   - テキスト: 最大 25K文字

2. **トークン管理修正**
   - `print()` → `logger.info()` に変更
   - 実際のトークン予算を渡す
   - Greedy allocation の検証

3. **エラーハンドリング**
   - try-except で例外をキャッチ
   - グラフ生成失敗時は非グラフ版を使用

### 中期（複数日で実装）

1. **スコアリング改善**
   - 問題記述に基づく意味的スコアリング
   - キーワード出現数でランキング
   - 構造情報は二次的に

2. **適応的グラフサイズ**
   - パフォーマンスを監視
   - 実際の改善がなければグラフを削減
   - インスタンスごとに最適化

### 長期（アーキテクチャ見直し）

1. **別々のパス実装**
   - グラフあり: 高精度（ただし条件付き）
   - グラフなし: 安定性重視
   - ユーザーが選択可能

2. **段階的グラフ構築**
   - 小さいグラフから開始
   - フォールバック時に削減
   - リトライ

## 結論

**RepoGraph 統合で精度が低下した主要な理由:**

1. **グラフコンテキストが大きすぎて LLM を混乱させる**
   - 84個の関数を見せて「行を探してください」は不可能
   - 最適: 6-15個、許容: 20個、限界: 50個

2. **スコアリングが構造的（グラフベース）で意味的ではない**
   - 「このファイルは構造的に関連」≠「この行は修正必要」
   - 意味的フィルタリングが必要

3. **トークン管理が失敗している**
   - 予算超過（8.4-130%）
   - Greedy allocation が機能していない（logging なし）

4. **サイレント失敗により全体の信頼性低下**
   - 4インスタンス処理失敗
   - 処理完了率が 95.7% → 78.3% に低下

**結果**: グラフ情報は「正しい方向だが、実装と適用方法が悪い」という状態
