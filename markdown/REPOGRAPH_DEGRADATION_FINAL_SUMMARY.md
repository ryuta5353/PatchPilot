# RepoGraph 統合によるファイルレベル精度低下の根本原因 - 最終分析サマリー

**実験**: Phase 2-6 Greedy Dynamic Token Allocation 実装（23インスタンス）

**結果**: ファイルレベル -5.6pp（77.8% → 72.2%）、ラインレベル -8.5pp（24.1% → 15.6%）

**原因**: グラフコンテキストが**構造的には正しいが、サイズが大きすぎて LLM を混乱させている**

---

## I. 問題の本質（一行で）

**グラフが大きければ大きいほど（セクション数が多いほど、関数数が多いほど）、LLM は「どの行を修正すればいいのか」判断ができなくなる。**

---

```
  関数位置数 ↑ → ラインレベル精度 ↓

相関: -0.95 (完全に逆相関)
```

### なぜファイルレベルは改善するのにラインレベルは悪化するのか

```
ファイルレベル:
  Q: 「どのファイルを修正？」
  A: グラフの依存関係 → 「このファイルは他と関連している」
     → 信頼できるヒント → 改善 ✓

ラインレベル:
  Q: 「どの行を修正？」
  A: グラフの 84個すべての関数定義
     → 「どれが重要なの？」
     → LLM が混乱 → 悪化 ✗

同じグラフが、階層によって「有用」にも「有害」にもなる
```

```
失敗の 4インスタンス:
```

## III. 実装レベルでの根本原因

### 原因 1: Composite Score が「すべての関連関数」を選出

```python
# repograph_utils.py:164-187

score = file_locality_score(file, related_locs)  # 1000/100/1
      + direct_neighbor_count(file)               # 関数数
      + in_degree_count(file)                     # 参照数

結果:
  storage.py: 1020 点 → 選出 → 全関数含める
  move.py:    108 点  → 選出 → 全関数含める
  ...

効果: 選出されたファイルの「すべての関数」が含まれる
結果: セクション 17個 × 関数 5-10個 = 85-170個の定義
```

### 原因 2: Greedy Allocation が機能していない

```python
# repograph_utils.py:316-405

期待: token_budget = 30,740 tokens
実測:
  平均: 33,313 tokens (+8.4% オーバー)
  最悪: 69,938 tokens (+2.3倍 オーバー)

原因:
  1. Token 推定が粗い（len(text) // 4）
  2. logger 出力がない（検証不可）
  3. def_tags が無条件に含まれる
  4. ref_tags の制限が機能していない
```

### 原因 3: デバッグ情報がログに出ない

```python
# repograph_utils.py:326, 391, 396

実装: print(f"[INFO]...")
問題: print() は logging に出ない
結果: Greedy allocation が動いているか検証不可

正しい実装: logger.info()
```

### 原因 4: サイレント失敗（エラーハンドリングなし）

```python
# localize.py:225

実装:
  result = localize_function_from_compressed_files(...)
  # try-except なし

結果:
  例外発生 → キャッチされない → 処理中断 → ログに出ない
  → ユーザーは何が起きたか分からない
```

## IV. メカニズム：LLM が混乱する理由

### LLM の認識プロセス

```
84個の関数をグラフコンテキストで見た場合:

1. 「すべてが『関連している』と言われている」
2. 「では、重要度の優先順位は？」
3. 「84個のうち、どれが最も重要？」
4. 「情報が多すぎて判断不可能」
5. 「ランダムに選ぶ」
6. 「ハズれ」

結果: 精度低下（最悪 -100pp）
```

### 最適なグラフサイズ

```
グラフに含まれる関数数  |  LLM の判断難易度  |  期待精度変化
─────────────────────────────────────────────────────
1-5個                  |  非常に容易        |  +10-15pp ✓✓✓
6-15個                 |  容易              |  +5-10pp ✓✓
16-30個                |  中程度            |  -1-3pp  ○
31-60個                |  困難              |  -5-10pp ✗
60個以上               |  不可能            |  -50pp以上 ✗✗
```

**現実**: sphinx-8595 は 84個 → LLM は判断不可 → -100pp

## VI. 修正のロードマップ

### Phase 1: 即座に実行（3-4時間）

1. **logger 出力に変更**
   ```python
   print() → logger.info()  # repograph_utils.py:326, 391, 396
   ```
   効果: Greedy allocation の動作が検証可能に

2. **エラーハンドリング追加**
   ```python
   try:
       result = localize_function_from_compressed_files(...)
   except Exception as e:
       logger.error(f"Failed: {e}")
       # non-graph path にフォールバック
   ```
   効果: サイレント失敗が 4インスタンスが処理完了

### Phase 2: 短期修正（1-2日）

3. **グラフサイズ制限**
   ```python
   max_tags_per_file = 10  # 関数数を 10個以下に制限
   max_sections = 8        # セクション数を 8個以下に制限
   max_chars = 25000       # テキストを 25K文字以下に制限
   ```
   効果: ラインレベル精度がベースラインに戻る、可能性あり

4. **Token 推定の改善**
   ```python
   from tiktoken import encoding_for_model
   enc = encoding_for_model("gpt-4o")
   tag_tokens = len(enc.encode(text))  # 正確な計算
   ```
   効果: 予算超過の問題が解決

### Phase 3: 中期改善（1週間）

5. **Composite Score を意味的に改善**
   ```python
   score = problem_statement_mentions(func) * 100
         + direct_neighbors(func) * 10
         + in_degree(func) * 1
   ```
   効果: 問題に本当に関連する関数を優先選出

6. **適応的グラフサイズ**
   - パフォーマンス監視
   - 改善がなければグラフを削減
   - インスタンスごとに最適化

## IX. 結論

### 問題の本質

RepoGraph は**理論的には正しい**が、**実装と適用方法が悪い**。

```
理論:   依存関係グラフで「関連関数」を示す → ファイル選択改善
実装:   84個すべての関数を提示 → LLM 混乱 → ラインレベル悪化
```

### 修正の見通し

```
短期(3-4時間):
  logger + エラーハンドリング追加
  → 信頼性 78.3% → 90%+

短期(1-2日):
  グラフサイズ制限 + token 推定改善
  → ラインレベル 15.6% → 20-22%
  → ファイルレベル 72.2% → 74-75%

中期(1週間):
  Composite Score + 動的グラフサイズ
  → ラインレベル 22-24%（ベースライン超過の可能性）
  → ファイルレベル 76-78%（ベースライン相当）
```

### 最後の言葉

**グラフコンテキストは「質 vs 量」の問題だ。**

- 小さく集約されたグラフ（8-10個の関数）→ 精度向上 ✓
- 大きく包括的なグラフ（84個の関数）→ 精度低下 ✗
