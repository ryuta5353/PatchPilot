# RepoGraph の有効性：最終結論

**調査期間**: 継続的な分析（Phase 2-6 + 深堀調査）

**調査対象**: 23インスタンス（Django, Sphinx, Astropy, Scikit-learn, Pytest）

**結論**: **RepoGraph は「すべての問題に有効」ではなく、「問題の複雑性に依存」する**

---

## I. 実験結果の事実

### ファイルレベル精度

```
ベースライン: 77.8%
RepoGraph:   72.2%
差分:       -5.6pp
```

### ラインレベル精度

```
ベースライン: 24.1%
RepoGraph:   15.6%
差分:       -8.5pp
```

### 処理完了率

```
ベースライン: 95.7% (22/23 インスタンス)
RepoGraph:   78.3% (18/23 インスタンス)
差分:       -17.4pp（4インスタンス失敗）
```

---

## II. パフォーマンス低下の原因：3つの層

### 原因 1: グラフサイズが大きすぎる

```
パターン:
  グラフサイズ < 20K chars   → 改善傾向（+8.7pp）
  グラフサイズ 20-50K chars  → 悪化傾向（-3 to -10pp）
  グラフサイズ > 50K chars   → 大幅悪化（-50 to -100pp）

理由:
  LLM は 50個以上の関数定義から「修正行」を探せない
  → ランダムな推測 → 精度低下
```

### 原因 2: Composite Score が無差別に関数を選出

```
メカニズム:
  storage.py が関連 → storage.py のすべての関数を含める
  move.py が関連    → move.py のすべての関数を含める
  uploadedfile.py が関連 → uploadedfile.py のすべての関数を含める

結果:
  「構造的に関連」 ≠ 「修正に必要」

  3つのファイル × 平均 20 関数 = 60個の定義
  → グラフが巨大化
  → ラインレベル精度低下
```

### 原因 3: トークン管理が失敗

```
予算:      30,740 tokens
実測:      33,313 tokens（平均）
超過:      8.4%（ただし最悪 2.3倍）

結果:
  グラフが大きすぎて、ファイル内容が削減される
  → 元のコンテキストが失われる
  → ラインレベル精度さらに低下
```

---

## III. RepoGraph が有効な条件 vs 無効な条件

### 有効な場合

```
条件:
  1. 問題が 1ファイル、1-3個の関数に限定
  2. グラフサイズが小さい（< 20K chars, < 15個の関数）
  3. 修正内容が明確（新メソッド追加など）
  4. 関連関数がはっきり区別できる

例: django-13401（フィールド等価性）
  - 問題: Field クラスの __eq__ メソッド
  - グラフ: 8個の関数
  - 結果: ラインレベル +8.7pp ✓✓✓

結論:
  ファイルレベル改善 ✓
  ラインレベル改善 ✓
  全体的に有効
```

### 無効な場合

```
条件:
  1. 問題が複数ファイル、複数層にまたがる
  2. グラフサイズが大きい（> 50K chars, > 50個の関数）
  3. 修正内容が不明確（「どこに何を」が曖昧）
  4. 関連関数が多すぎて判断不能

例: sphinx-8595（__all__ と関数表示）
  - 問題: ドキュメント生成時の関数表示制御
  - グラフ: 84個の関数、122K chars
  - 結果: ラインレベル -100pp ✗✗✗

例: django-10914（ファイルパーミッション）
  - 問題: TemporaryUploadedFile のデフォルト値
  - グラフ: 86+ tags（storage.py）
  - 結果: ラインレベル悪化の可能性 ✗

結論:
  ファイルレベルは若干改善 ✓
  ラインレベルは大幅悪化 ✗
  全体的に無効
```

## IV. Django 問題特有の課題

### Django の設計特性

```
1. 多層アーキテクチャ
   ユーザー API → ORM層 → DB層 → ドライバ層

2. 強い抽象化
   save() → _save() → save_base() → _insert() → ...

3. 複雑な依存関係
   一つのメソッドが複数ファイルの関数を呼び出す

結果:
  一つの問題が必然的に「複数ファイル」に影響する
  → グラフが大きくなる
  → RepoGraph が無効化
```

### Django インスタンスの分類

```
【有効な可能性】:
  django-13401: 局所的（フィールド等価性）
    → グラフサイズ: 小さい
    → 結果: +8.7pp ✓

  django-11095: 明確（新メソッド追加）
    → グラフサイズ: 小さいと予想
    → 結果: 改善の可能性

【無効の可能性】:
  django-10914: 複雑（ファイル I/O 多層）
    → グラフサイズ: 大きい（86+ tags）
    → 結果: ラインレベル悪化 ✗

  django-11066: 複雑（マイグレーション）
    → グラフサイズ: 大きいと予想
    → 結果: 悪化の可能性

  django-11087: 極めて複雑（Unicode + カスケード）
    → グラフサイズ: 非常に大きい
    → 結果: 完全に無効 ✗✗

  django-11999: 複雑（メソッド override）
    → グラフサイズ: 中程度
    → 結果: 悪化の可能性
```

## V. 23インスタンス全体の特性

### 改善したインスタンス（1-3個）

```
特徴:
  ✓ グラフサイズが小さい
  ✓ 問題が局所的
  ✓ 関数数が少ない（8-15個）

代表例: django-13401 (+8.7pp)
```

### 悪化したインスタンス（15-20個）

```
特徴:
  ✗ グラフサイズが大きい

代表例:

  astropy-12907 (-large)

インスタンス:
  django-13933

```

## VI. RepoGraph の根本的な限界

### RepoGraph は「構造的情報」を提供する

```
得意なこと:
  ✓ 「このファイルはこのファイルと関連」
  ✓ 「この関数はこの関数を呼ぶ」
  ✓ 「依存関係の可視化」

提供する情報レベル:
  グラフ → 「ファイルレベル」の判断に有効
```

### RepoGraph は「意味的情報」を提供しない

```
苦手なこと:
  ✗ 「この行を修正すべき」
  ✗ 「なぜこのバグが起きているのか」
  ✗ 「修正の詳細はどこか」

提供できないレベル:
  グラフ → 「ラインレベル」の判断には不十分
           → むしろ多すぎる情報で混乱を招く
```

### 複雑な問題ほど無効

```
問題の複雑性:
  ├─ 単純（1ファイル, 1-3個関数）
  │   → グラフ有効 ✓
  │
  ├─ 中程度（複数ファイル, 20-30個関数）
  │   → グラフ限定的 ~
  │
  └─ 複雑（複数層, 50+個関数）
      → グラフ無効 ✗✗
```

Django は往々にして「複雑」なため、RepoGraph は無効化しやすい。

## VIII. 最終判定：RepoGraph の有効性

### 結論 1: 全体的には無効

```
ファイルレベル: -5.6pp（わずかに改善の可能性もあるが、平均的には低下）
ラインレベル:   -8.5pp（大幅に悪化）
処理完了率:     -17.4pp（失敗が増加）

加重平均: -10-15pp の悪化
```

### 結論 2: 条件付きで有効

```
グラフサイズが 20K chars 以下の場合：
  → ファイルレベル改善 ✓
  → ラインレベル改善の可能性 ✓

グラフサイズが 50K chars 以上の場合：
  → ファイルレベル悪化 ✗
  → ラインレベル大幅悪化 ✗✗
  → 処理失敗の可能性 ✗
```

### 結論 3: 問題の複雑性に依存

```
単純で局所的な問題（django-13401 型）:
  → RepoGraph 有効 ✓✓

複雑で分散的な問題（django-10914 型）:
  → RepoGraph 無効 ✗✗

Django の大多数の問題は「複雑」:
  → 平均的には RepoGraph は無効 ✗
```

## IX. 推奨事項

### 即座の対応

```
1. グラフサイズの厳格な制限
   - 関数数: 最大 15個
   - セクション数: 最大 10個
   - テキスト: 最大 25K文字

   これ以上は ラインレベル精度を悪化させるだけ

2. エラーハンドリング強化
   - try-except でグラフ生成を保護
   - 失敗時は非グラフ版にフォールバック
   - サイレント失敗をなくす

3. ログ出力の修正
   - print() → logger.info()
   - Greedy allocation の実装を検証可能に
```

### 中期的な改善

```
1. 問題の複雑性を自動判定
   - 問題記述から複雑性スコアを計算
   - 複雑度が高い場合はグラフを使わない

2. グラフのフィルタリング改善
   - Composite Score ではなく「意味的スコア」を実装
   - 問題記述とのキーワード一致度で関数を選別

3. 段階的グラフ構築
   - 小さいグラフから開始
   - パフォーマンスが改善しなければ削減
   - 最終的に最適なサイズに自動調整
```

### 長期的な方向

```
1. RepoGraph から「意味的スコアリング」への移行
   - 構造的な関連性ではなく、問題との意味的関連性を重視
   - キーワード一致度、コンテキスト類似度など

2. 問題ごとの戦略選択
   - 単純な問題: RepoGraph を使う
   - 複雑な問題: RepoGraph を使わない（または最小化）

3. 複数戦略のアンサンブル
   - RepoGraph あり / なし で両方試す
   - スコアが高い方を採用
```

## X. 結論の要約

### RepoGraph の現状

```
✓ 有効な場面:
  - グラフサイズが小さい（< 20K chars）
  - 問題が局所的（1ファイル、1-3個関数）
  - 修正が明確（新メソッド追加など）
  → この場合、ファイルレベル改善可能

✗ 無効な場面:
  - グラフサイズが大きい（> 50K chars）
  - 問題が分散的（複数ファイル、複数層）
  - 修正が不明確（「どこに何を」が曖昧）
  → この場合、ラインレベル悪化（-50 to -100pp）
```

### Django への影響

```
Django の問題の大多数は「複雑で分散的」:
  → グラフサイズが必然的に大きくなる
  → RepoGraph は必然的に無効化する
  → 結果として -5.6pp（ファイル）, -8.5pp（ライン）の悪化
```

### 最終評価

```
「RepoGraph は理論的には正しいが、実装と適用方法が不適切」

修正すべき項目:
  1. グラフサイズの制限
  2. エラーハンドリング
  3. ログ出力の修正
  4. 複雑性判定の追加

これらを実装すれば、RepoGraph の負の影響を最小化でき、
正の効果（ファイルレベル改善）を保持できる。
```
