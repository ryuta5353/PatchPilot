# RepoGraph 論文 vs 我々の実装：根本的な相違の発見

**作成日**: 2025-11-10
**重要性**: ⭐⭐⭐⭐⭐ 極めて重要な発見

---

## 最重要な発見：グラフサイズが正反対

### 論文での成功例（RepoGraph原著）

**Agentless + RepoGraph の結果：**
```
ファイルレベル: 68.7% → 74.3% (+5.6pp) ✓ 改善

グラフコンテキストサイズ：
- 1-hop: 平均 11.6 ノード, 37.1 エッジ, ~2,311 トークン
- 2-hop: 平均 54.5 ノード, 89.9 エッジ, ~10,505 トークン

論文での推奨: **1-hop が最適。2-hop はパフォーマンス悪化**
```

### 我々の失敗例（PatchPilot Phase 2-6）

**Baseline vs RepoGraph の結果：**
```
ファイルレベル: 77.8% → 72.2% (-5.6pp) ✗ 悪化

グラフコンテキストサイズ：
- 実際: 113,292 文字 ≈ 28,323 トークン
- セクション数: 31
- ロケーション数: 113
```

## 根本的な相違の分析

### 相違点1：グラフサイズ

| 項目 | 論文（1-hop） | 論文（2-hop） | 我々の実装 |
|------|-------------|-------------|---------|
| **ノード数** | 11.6 | 54.5 | 不明（113ロケーション） |
| **トークン数** | 2,311 | 10,505 | **28,323** |
| **パフォーマンス** | +5.6pp ✓ | パフォーマンス悪化 ✗ | -5.6pp ✗ |

**結論**: 我々のグラフは、論文の2-hop版より大きく、論文でも「パフォーマンス悪化」と明記されているサイズを超えている。

### 相違点2：グラフ構築戦略

**論文（RepoGraph）：**
```
方法論: k-hop ego-graph retrieval
  - 検索単語（関数名など）を中心に構造的距離で取得
  - Simple is better（1-hopが最適）
  - 関連度スコアリングなし（構造的距離のみ）
```

**我々の実装（Phase 2-6）：**
```
方法論: Composite Score による複雑なスコアリング
  - ファイル近接性スコア: 1000/100/1
  - 直接的な隣人ボーナス: +50
  - In-degree 補助スコア: 0-10
  - def/ref タグの分別
  - 動的トークン配分（Greedy allocation）

複雑さ: 論文の実装より格段に複雑
```

**論文の示唆**: 「複雑なスコアリングが逆効果だった可能性」

### 相違点3：プロンプトへの統合方法

**論文（RepoGraph）：**
```
位置: "Function/Class Dependencies" セクション
  - localization と edition 両段階で使用
  - 関数/クラス依存関係として明示的に構造化
  - シンプルなテキストフラッテン

トークン削減なし：
  - グラフを追加しても、他のコンテンツを削減しない
  - グラフサイズが小さいため（1-hop: 2,311トークン）
```

**我々の実装（Phase 2-6）：**
```
位置: 複数の "### Dependencies for FUNCTION_NAME" セクション
  - Fine-Grain Level のみで使用
  - 113,292 文字の大量コンテンツ

トークン削減あり：
  - グラフを追加するとプロンプト超過
  - 他の情報（ファイルコンテキスト）を削減
  - 50,182トークン の情報喪失
```

### 相違点4：適用段階

**論文（RepoGraph）：**
```
どのフェーズで使用？
  - "localization" 段階メイン
  - "edition"（修復）段階にも使用

フェーズ分離なし：
  - 同じ依存関係を両段階で活用
```

**我々の実装（Phase 2-6）：**
```
どのフェーズで使用？
  - Fine-Grain Level（Localization の最終段階）のみ

トークン管理：
  - Repair フェーズとの統合を考慮していない
  - Localization 単体で 28,323 トークン消費
```

## パフォーマンスの正反対の理由

### 論文が成功した条件

1. **グラフサイズの最適化**
   ```
   1-hop版を選択：2,311トークン（最適）
   2-hop版を拒否：10,505トークン（パフォーマンス悪化）
   ```

2. **シンプルな関連度判定**
   ```
   構造的距離（k-hop）のみ使用
   複雑なスコアリングなし
   ```

3. **トークンの効率的利用**
   ```
   グラフコンテキストが小さい（2,311トークン）
   → 他の情報を削減不要
   → プロンプト情報量が増加
   ```

4. **統合設計の明確性**
   ```
   "Function/Class Dependencies" セクションに埋め込み
   他のセクションと明確に分離
   ```

### 我々が失敗した理由

1. **グラフサイズの膨張**
   ```
   28,323トークン（論文の12倍以上）
   → トークン制限に引っかかる
   → 他の情報を大幅削減
   ```

2. **複雑な関連度スコアリング**
   ```
   Composite Score の導入
   → 関連度判定が不正確化
   → グラフがノイズ化
   ```

3. **動的トークン配分の失敗**
   ```
   Greedy allocation で 30,740 トークン割り当て
   → 実際の利用可能予算と乖離
   → ファイルコンテキスト削減（-50,182トークン）
   ```

4. **統合設計の複雑化**
   ```
   複数の "### Dependencies" セクション
   → プロンプトが散乱
   → グラフとコンテキストの競合
   ```

## 論文での明確な警告

### 論文の記述

> "**2-hop variants performed worse** when simply flattened"

つまり、論文では：
- 1-hop: 最適（+5.6pp改善）
- 2-hop: パフォーマンス悪化（テストでも確認）

### 我々への示唆

**113ロケーション、28,323トークンのグラフは、実質的に「多すぎるホップ距離」と等価**

```
k=1: 11.6 ノード (2,311トークン) → +5.6pp ✓
k=2: 54.5 ノード (10,505トークン) → 悪化 ✗
k=∞: 113 ロケーション (28,323トークン) → -5.6pp ✗
```

## なぜ論文の実装は成功し、我々は失敗したのか

### 論文の哲学
```
"Less is more"
- 1-hop の関連度情報で十分
- シンプルな構造的距離のみ
- 小さなグラフサイズ
- トークン効率が高い
```

### 我々の誤り
```
"More is better"（逆効果）
- 無制限のロケーション収集
- 複雑な複合スコアリング
- 大きなグラフサイズ
- トークン予算圧迫
- 他の情報が削減される
```

## 改善への推奨

### 短期的修正（論文の実装に近づく）

**1. グラフを k=1 に制限**
```python
# 現在
graph_context = construct_code_graph_context(
    found_related_locs,
    code_graph,
    graph_tags,
    structure,
    preferred_files=pred_files,
    logger=logger
)  # → 113 ロケーション

# 改善後
graph_context = construct_code_graph_context(
    found_related_locs,
    code_graph,
    graph_tags,
    structure,
    max_hops=1,  # ← 1-hop のみ
    preferred_files=pred_files,
    logger=logger
)  # → ~10-15 ロケーション
```

**2. Composite Score を削除**
```python
# 現在
return locality_score + neighbor_bonus + in_degree_score

# 改善後
return in_degree_score  # シンプルな構造的重要度のみ
```

**3. トークン予算を現実的に設定**
```python
# 現在
total_token_budget=30,740  # 固定

# 改善後
total_token_budget=2,311   # 論文の1-hop相当
```

**予期される効果**：
- グラフサイズ削減（28,323 → 2,311トークン）
- トークン予算に余裕
- ファイルコンテキスト喪失なし

## Agentless + RepoGraph の実装確認

### 論文での実装

RepoGraph + Agentless は:
1. **Procedural framework** を採用
   - グラフコンテキストを "flattened into the template"
   - Function/Class Dependencies セクションに統合

2. **1-hop ego-graph** のみを使用
   - 平均 11.6 ノード
   - 2,311 トークン
   - 最適なパフォーマンス

3. **結果: +5.6pp の改善**
   - Agentless 単体: 68.7%
   - Agentless + RepoGraph: 74.3%

### 我々の実装

Phase 2-6 では:
1. **複雑な Composite Score** を導入
   - ファイル近接性、隣人ボーナス、in-degree
   - 論文にない独自実装

2. **無制限のロケーション収集**
   - 113 ロケーション
   - 28,323 トークン
   - 論文の 12 倍以上

3. **結果: -5.6pp の悪化**
   - Baseline: 77.8%
   - RepoGraph: 72.2%
